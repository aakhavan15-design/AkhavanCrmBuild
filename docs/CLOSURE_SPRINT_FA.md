# AKHAVAN CRM — برنامه پایان‌دار تحویل نسخه اجرایی

وضعیت این سند: W0 تا W7 مأموریت‌های بسته مالی هستند، نه سقف دامنه توسعه. طبق مصوبه مالک ۲۰۲۶-۱۱-۲۵، همه فازهای مستقل ادامه می‌یابند. نقص واقعی خارج از این بسته در چک‌لیست فعال با شناسه یکتا ثبت می‌شود.

## قوانین توقف حلقه

1. وضعیت توسعه (`COMPLETE / PARTIAL / MISSING / FROZEN`) مستقل از پذیرش (`PASS / FAIL / NOT TESTED / EXTERNAL BLOCKED`) است. صرف وجود فایل یا UI شاهد COMPLETE نیست؛ صرف فقدان تست نیز شاهد PARTIAL یا MISSING نیست. وضعیت قدیمی Wها سابقه مأموریت است و به‌تنهایی دستور بازنویسی نیست.
2. DONE با شکست آزمون رفتاری خودش باز می‌شود، نه با «ممیزی جدید» یا سلیقه عامل.
3. حداکثر دو تلاش هدفمند برای یک نقص؛ سپس مانع مشخص (مسیر/شاهد/وابستگی) و رفتن به آیتم بعدی. قانون قدیمی «حداکثر ۱ تا ۳ ردیف در نوبت» در این Sprint اعمال نمی‌شود.
4. هر مرحله یک Commit/Push قابل ردیابی، آزمون رفتاری و تغییر وضعیت با SHA دارد. هیچ ادعای PASS بدون خروجی واقعی.
5. طراحی مصوب، Chat/Groups، ناوبری، هدر و Landing قفل‌اند؛ موتور مالی موازی یا داده Fake ممنوع.
6. مانع محیطی SQL/ERP فقط Gate پذیرش زنده را BLOCKED می‌کند. توسعه مستقل متوقف نمی‌شود.
7. محاسبات رسمی تنها از مالی/ERP و مسیر DataProvider؛ صفر و UNAVAILABLE دو مفهوم متفاوت هستند.
8. شمارش چک‌لیست فقط با `node scripts/checklist_status.mjs --check` و `--write`. سابقه‌ها در `CHECKLIST_HISTORY_FA.md`.

## دروازه‌های پذیرش دودویی برای هر گزارش

| گیت | الزام | روش تأیید |
|---|---|---|
| G1 | منبع داده رسمی/برچسب تازگی و پوشش | تست provider + عدم READY ساختگی |
| G2 | یک محاسبه‌گر مرجع، تطبیق سناریوها | تست رفتاری با خروجی عددی |
| G3 | Loading/Empty/Error/UNAVAILABLE شفاف | تست حالت‌ها |
| G4 | فیلتر و Drill-down تا سند/ردیف | تست فیلتر و ناوبری |
| G5 | RBAC در API و Scope یکسان در لیست/جزئیات | تست منع دسترسی |
| G6 | پایداری نتیجه پس از Refresh/Sync/تصحیح سند | تست یکپارچگی هدفمند |
| G7 | UI قفل‌شده، RTL، موبایل/کیبورد و عدم خطای Build | Build هدفمند + پذیرش دستگاه |

پذیرش عملیاتی PASS نیازمند هر ۷ گیت است. اگر G5/G6 نیازمند SQL واقعی است، Verification را EXTERNAL BLOCKED ثبت کن؛ Development را مستقل و بر اساس شواهد اتصال و شکاف واقعی تعیین کن.

## مأموریت‌های بسته

| شناسه | خروجی و شرط خاتمه | وضعیت فعلی |
|---|---|---|
| W0 | حذف شمارش‌های دستی/آرشیو اجراهای قدیمی؛ یک شمارنده؛ ادغام/حذف موتور Candidate؛ اصلاح قراردادهای فاسد | IN PROGRESS |
| W1 | مانده دفتری قطعی از مالی؛ تسویه قدیمی‌ترین فاکتور در FIFO و نمایش فاکتور باقی‌مانده با LIFO مالی؛ ۳+۷+۸+۱۲ و مانده ۲۵ ⇒ ۱۲+۸+۵ | IN PROGRESS |
| W2 | P&L رسمی فقط دفتر معتبر؛ unmapped به عنوان عدم پوشش؛ مقایسه دوره‌ای | IN PROGRESS |
| W3 | یک موتور نقدینگی آینده؛ بانک، چک، تعهد و سناریو بدون دوباره‌شماری | IN PROGRESS |
| W4 | فروش خالص واحد در همه گزارش‌ها از فروش ناخالص منهای برگشتی قطعی؛ روز فقط برگشتی، مقایسه دوره‌ای، سهم مشتری | IN PROGRESS |
| W5 | **CRM خودش FIFO را** از موجودی ابتدای دوره + گردش ERP محاسبه و در DB CRM ذخیره می‌کند؛ InvoiceEvidence و سود فقط خروجی موتور واحد را می‌خوانند؛ خرید/انبارداری موازی ERP ایجاد نمی‌شود | IN PROGRESS |
| W6 | ویزیت و مشتری جاافتاده از مسیر واقعی ERP، با شواهد عدم سفارش و پوشش زون | IN PROGRESS |
| W7 | تفکیک فیزیکی ReportEngine به اجزای موضوعی بدون حذف ۱۱ گزارش یا ایجاد تب جدید؛ تطبیق رفتاری قبل/بعد | IN PROGRESS |

این جدول وضعیت تاریخی مأموریت‌ها را نشان می‌دهد؛ وضعیت توسعه و پذیرش باید به‌صورت مستقل با شواهد تعیین شود. هر مانع باید همراه نام فایل، نتیجه تست و منبع داده در گزارش پایان درج شود.

## ترتیب توقف

W0 → W4 (ریسک عدد فروش غلط) → W1 (مطالبات) → W2 → W3 → W5 → W6 → W7؛ این ترتیب پس از بررسی وابستگی‌های واقعی است، نه فهرست فازهای قدیمی. پایان توسعه این Sprint = همه شکاف‌های مستقل Wها رفع شده‌اند؛ پذیرش خارجی در صف جدا با علت و خروجی قابل بازیابی ثبت می‌شود. ورود به نسخه اجرایی نیازمند پذیرش SQL/ERP واقعی و مجوزهای نقش‌های عملیاتی است.
