# AKHAVAN CRM — بسته تحویل برای پذیرش ERP / SQL / TypeScript

**تاریخ ثبت:** ۱۴۰۵/۰۹/۰۳. **مرجع اجرا:** شاخه `main` و آخرین کامیت موفق/ناموفق CI آن؛ نسخه جداگانه، Branch توسعه موازی یا داده نمونه به‌عنوان شاهد پذیرش معتبر نیست.

## وضعیت دقیق خروجی
- **کاتالوگ شاخص‌ها:** `src/lib/metricRegistry.ts` شامل ۲۶ تعریف کددار، نسخه، فرمول، منبع و وضعیت. Seed SQL متناظر `019_kpi_catalog_v2_generated.sql`؛ این کاتالوگ تنها «تعریف و نگاشت» است، نه اثبات اینکه همه صفحات تنها یک engine دارند.
- **فروش خالص:** `shared/financialArithmetic.mjs` فرمول مشترک Gross minus posted sales returns برای Node و React است؛ `src/lib/financialMetricKernel.ts` مالک تجمیع فاکتور، برگشت، انتساب به مشتری و `reconcileNetSales` در مقابل دفتر قطعی ERP. فروش خالص رسمی فقط اگر منابع و ledger هر دو در همان دوره و دامنه match شوند منتشر می‌شود.
- **برگشت بدون مبنا:** برگشت قطعی ERP با مشتری معتبر، بدون شماره فاکتور، وارد فروش خالص مشتری و شرکت می‌شود؛ به فاکتور یا فروشنده تخصیص حدسی ندارد. فاکتور مبنای اشاره‌شده ولی پیدا نشده خطاست.
- **فروشنده:** `attributeReconciledSalesBySeller` فقط از همان factهای مرکزی استفاده می‌کند و مجموع سهم را با فروش خالص دفتر تطبیق می‌دهد. موارد برگشتی غیرقابل انتساب ⇒ Unavailable، نه سهم ساختگی.
- **مطالبات:** مانده قطعی از `getDetailSubsidiaryBalances` و `resolveCustomerBalanceView`، توزیع LIFO نمایشی از `agingBuckets.ts`، FIFO تسویه بر اساس داده رسمی. کارت Customer360 و فیلترهای گزارش مالی باید همین مسیر را بخوانند؛ `invoice.balance` فقط شاهد کنترل اختلاف است، نه مانده رسمی.
- **نقشه:** `server/routeMapMoney.mjs` از همان `calculateNetSalesCore` استفاده می‌کند؛ چون گزارش نقشه هنوز proof تطبیق دفتر در دامنه مسیر ندارد، انتشار فروش خالص و تحقق هدف مسیر مسدود است. این وضعیت عمداً fail-closed است و هنگام تست زنده باید به جای ساخت مبلغ موازی، source-scope reconciliation افزوده شود.
- **عملیات:** `src/lib/operationsEngine.ts`، گزارش سود/مطالبات بدون proof دفتر و برگشتی ناقص عدد قطعی تولید نمی‌کند. برآوردهای سفارش/پیش‌فاکتور با برچسب برآوردی از گزارش مالی قطعی جدا هستند.
- **حقوق و پورسانت:** `executePayrollRun` فقط با `financialEvidence: {ledgerReconciled:true,periodMonth,netSalesBySeller}` به نرخ پورسانت دست می‌زند؛ جمع فاکتور ناخالص هیچ پورسانت قطعی ایجاد نمی‌کند. اتصال واقعی data pipeline به این ورودی هنوز نیازمند پذیرش ERP/SQL است.
- **ReportsHub:** محاسبات gross فاکتورها فقط عنوان «ناخالص» دارند؛ تحقق هدف از آنها جعل نمی‌شود، گزارش فروشندگان و هدف به گزارش تحلیلی مبتنی بر تطبیق دفتر هدایت می‌شوند.
- **پیشنهادهای هوش فروش:** خروجی مبتنی بر پیش‌فاکتور فقط «ارزش پیش‌فاکتور و روند پیشنهاد» نام دارد؛ درآمد یا فروش قطعی نامیده نمی‌شود.

## ممیزی قابل بازتولید
اجرای `node scripts/audit_kpi_consumers.mjs --json` در GitHub Actions بر ۳۳۱ فایل اجرایی انجام شد: ۷۰ فایل دارای اشاره به KPI، ۲۴ فایل دارای ارجاع به ماژول‌های مرجع، ۴۵ نشانه قابل‌بررسی در ۲۰ فایل در اولین اجرا. این عدد **اشکال ثابت‌شده نیست**؛ موارد seed/demo، جمع ناخالص سفارش، جمع پیش‌فاکتور و مقایسه `invoice.balance` برای کشف اختلاف false positive هستند. هربار خروجی JSON در Artifact workflow `KPI consumer source audit` ثبت می‌شود. فهرست باز را فقط بعد از اثبات موردی اصلاح کنید؛ حذف تست یا بازنویسی فرمول‌ها برای سبز کردن شمارنده ممنوع است.

## هفت دروازه قابل اندازه‌گیری برای تست فردا
1. **Contract schema:** اجرای idempotent همه migrationها به ترتیب؛ جدول‌های `DispatchPlan/Line`، Journal و CreditNote موجود بررسی شوند؛ migrations 055/056 بدون جدول حمل موازی و بدون schema drift. نتیجه PASS/FAIL و نسخه اجرا ثبت شود.
2. **ETL completeness:** برای یک Tenant/Source/Currency/Date window، شمارش و کنترل uniqueness فاکتور، ردیف، برگشت بدون مبنا، سند قطعی/غیرقطعی، mapping حساب و روش حمل؛ counts source ERP با CRM mirror یکی باشند. با نقص فید، `UNAVAILABLE`، نه صفر.
3. **Finance reconcile:** فروش ناخالص، برگشتی (دارای فاکتور/بدون مبنا)، خالص و سرفصل دفتر مالی در ریال برابر باشند؛ اختلاف tolerance حداکثر ۰٫۰۱ ریال در تست کنترل‌شده؛ ارقام خیلی بزرگ با decimal-string SQL نه float محاسبه شوند. مانده دفتری فقط اسناد قطعی، مانده کلی جدا.
4. **Receivables FIFO/LIFO:** با داده شناسه‌دار چند مشتری، تسویه قدیمی‌ترین فاکتور اول؛ باقیمانده نمایش آخرین فاکتور اول؛ جمع مانده فاکتورهای پوشش‌یافته + مبلغ بدون انتساب = مانده دفتری رسمی؛ هیچ سند دریافت بعدی بدون شماره حمل به نقدینگی حمل قبلی نچسبد.
5. **Permissions/tenant:** همه APIهای مالی/حمل برای بدون Token→401، بدون نقش→403، شعبه/فروشنده خارج دامنه→عدم افشا؛ query SQL حتماً tenant scoped و دارای مجوز حوزه باشد. test RLS live لازم است.
6. **UI + KPI parity:** همان بازه، شرکت، واحد پول، فیلتر مشتری/فروشنده/برند در ReportEngine، Finance، Customer360، ReportsHub، Operations و Route Map؛ نتایج یک شاخص رسمی باید دقیقاً برابر یا صریحاً UNAVAILABLE باشند. سناریو مرورگر موبایل/دسکتاپ و CSV نیز بررسی شود.
7. **Build/CI:** workflow رفتار اختصاصی، Vite production build، `tsc --noEmit`، UX quality و تست مرورگر باید همگی PASS شوند. فعلاً تست رفتار و Build پاس شده اما global TypeScript/UX quality FAIL است. پایان پروژه با تغییر دستی چک‌لیست اعلام نشود.
