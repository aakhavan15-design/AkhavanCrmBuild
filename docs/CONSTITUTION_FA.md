# قانون اساسی توسعه AKHAVAN CRM — ۲۰۲۶

## A. صحت و عدم جعل
- PASS فقط پس از اجرای واقعی آزمون و ثبت دستور/نتیجه.
- NOT VERIFIED برای موردی که امکان بررسی کامل آن فراهم نشده است.
- BLOCKED همراه علت و پیش‌نیاز مشخص.
- داده، KPI، پاسخ ERP، تراکنش مالی، تأییدیه یا تست ساختگی ممنوع.
- وضعیت منبع: LIVE / LOCAL / DEMO / PARTIAL / STALE / UNAVAILABLE.
- داده ناقص NULL بماند؛ هیچ مبلغ/بها/تاریخ/مختصاتی با حدس تکمیل نشود.

## B. عدم تکرار و عدم تخریب
- قبل از ایجاد، کل سورس، تست‌ها، routes، schema، migrations و docs را جست‌وجو کن.
- موتور، store، provider، API، جدول، workflow یا منبع حقیقت موازی ممنوع.
- هیچ فایل/قابلیت سالمی را بدون audit مصرف‌کنندگان حذف نکن.
- تغییر باید کوچک، متمرکز، قابل بازگشت و همراه regression test باشد.
- رفتار عمومی، نام فیلد، API و migration را بی‌دلیل نشکن.

## C. مرز ERP/CRM
- ERP مرجع حقیقت رسمی اسناد و عملیات مالی/انبار است.
- quote سفارش نیست؛ فاکتور رسمی فقط از ERP؛ CRM موفقیت ERP را جعل نمی‌کند.
- داده بیرونی read-only mirror با source identity و lineage است.
- ثبت CRM-owned فقط برای موجودیت‌هایی که واقعاً متعلق به CRM هستند.
- **مانده مالی = تفصیلی × معین (اصل الزامی در همه‌جا):** مانده هیچ شخص/موجودیت (مشتری، تأمین‌کننده، تولیدکننده، پرسنل، بانک، سایر) فقط در سطح کد تفصیلی محاسبه نمی‌شود؛ برای هر ترکیب معتبر «تفصیلی + معین (+ کل و سایر ابعاد در صورت وجود)» گردش بدهکار، گردش بستانکار و مانده مستقل = Σبدهکار − Σبستانکار از اسناد/گردش واقعی ERP استخراج و ماهیت آن (مثبت=بدهکار، منفی=بستانکار، صفر=تسویه‌شده) نمایش داده شود. هر تفصیلی می‌تواند به چند معین وصل شود بدون ادغام مانده‌ها؛ ریز گردش/اسناد هر معین قابل‌مشاهده باشد؛ جمع کل تفصیلی فقط کنار مانده‌های تفکیکی می‌آید و جایگزین آن‌ها نیست. CRM کد معین یا گردش موازی اختراع نمی‌کند و کدینگ ERP را حفظ می‌کند؛ نبود داده/نگاشت معتبر ⇒ «نامشخص/فاقد نگاشت»، هرگز مانده ساختگی.

## D. داده و پایگاه داده
- IndexedDB/LocalStorage/آرایه‌های seed یا cache محلی هرگز منبع حقیقت داده عملیاتی نیستند؛ فقط در تست/دمو یا cache موقتِ صریحاً مجاز و با برچسب منبع قابل استفاده‌اند. در اجرای عملیاتی، نبود اتصال/جدول/داده SQL Server باید خطای شفاف `UNAVAILABLE/BLOCKED` بدهد؛ fallback خاموش به داده محلی ممنوع است.
- SQL Server migrations افزایشی، idempotent، tenant-scoped و با RLS موجود.
- قبل از DDL همه migrationها، FK، index، RLS، naming و مصرف‌کنندگان بررسی شوند.
- dedupe و replay باید idempotent باشند؛ stale source حق overwrite داده تازه ندارد.
- هیچ جدول/ستون جدید بدون نیاز گزارش/قابلیت و قرارداد داده ساخته نشود.

- **معماری داده‌محور و آمادهٔ سرور (الزام):** همهٔ اطلاعات، گردش‌ها، مانده‌ها، ارتباطات و تنظیمات از دیتابیس می‌آیند؛ State/Store/Context/آرایهٔ ثابت فقط برای وضعیت موقت UI (پنجره، تب، فیلتر جاری، بارگذاری) است و منبع داده اصلی نیست؛ پس از Refresh داده باید از دیتابیس بازیابی شود. `DataProvider` تنها لایهٔ دسترسی است (دریافت، ثبت، ویرایش، حذف با قید تجاری، جست‌وجو/فیلتر، صفحه‌بندی، روابط، گردش مالی، مانده، خطا/وضعیت اتصال، تراکنش در صورت پشتیبانی)؛ هیچ صفحه/کامپوننت/موتور/گزارشی مستقیم به State، داده نمونه یا ذخیره‌سازی مستقل وصل نشود و دسترسی به DB داخل کامپوننت نباشد. قراردادهای Provider مستقل از محیط ثابت‌اند؛ تفاوت محلی/سرور فقط در تنظیمات محیط و Provider زیرساخت است؛ جدول‌ها و Migrationها قابل‌انتقال به سرور؛ لایهٔ یکپارچه‌سازی ERP مستقل؛ جابه‌جایی به سرور بدون بازنویسی صفحات و منطق تجاری. دیتابیس SQL Server متصل‌شده منبع حقیقت عملیاتی است؛ هیچ دیتابیس محلی/مرورگری جایگزین آن نیست. State فقط وضعیت موقت رابط کاربری است؛ cache فقط با سیاست مصوب، TTL، منبع/زمان/تازگی قابل‌مشاهده و بدون امکان جعل LIVE مجاز است. قابلیت پیاده‌نشده شفاف ثبت شود، نه داده ساختگی.
- **الزام ذخیره FIFO در دیتابیس خودمان:** اگر محاسبه FIFO/موجودی انبار لازم شود (با هر طرحی)، لایه‌ها و مصرف آن‌ها در دیتابیس CRM ذخیره می‌شوند، نه State/آرایهٔ موقت: لایهٔ موجودی (کالا، انبار، تاریخ ورود، مرجع سند رسید/برگشت، تعداد اولیه/باقی‌مانده، بهای واحد، منبع و وضعیت تأیید) و ریز مصرف لایه (مرجع فروش/خروج/برگشت، تعداد، بهای مصرف‌شده) با Migration افزایشی (ابتدا ممیزی `ProductCostMirror`/`InventorySnapshotMirror`؛ جدول موازی نسازید)؛ محاسبه و بازیابی فقط از مسیر `DataProvider`؛ ماندهٔ لایه‌ها قابل بازتولید از گردش (replay idempotent)؛ تا کامل‌بودن گردش‌ها نمایش `NOT VERIFIED`؛ مشخصات کالا از ERP فقط‌خواندنی می‌ماند.
- **تخصیص دریافت↔فاکتور مبنای مانده/سررسید نیست (قاعدهٔ مالک ۱۴۰۵/۰۸/۲۵):** مانده فقط از گردش مالی است؛ تخصیص‌های ثبت‌شده در CRM در ERP اعمال نمی‌شوند و ترتیب تسویه فاکتورها در ERP (از صورتحساب، به‌ترتیب از آخرین فاکتور به بالا) ثابت و قابل‌اثبات نیست. «کدام فاکتور تسویه شد» نامشخص است و هرگز از تخصیص CRM استنباط نمی‌شود. **سیاست مصوب مالک برای سنی مطالبات:** فقط «تخمینی» و با برچسب: مانده دفتری بدهکار هر مشتری از آخرین فاکتور شروع می‌شود و اگر بدهی بیشتر بود به فاکتور قبل می‌رود (`estimateLedgerAging`)؛ مازاد/فاکتور بی‌سررسید = «بدون انتساب»؛ بدون مانده بدهکار یا فاکتور ⇒ «نامشخص».
- **کلید مانده در دیتابیس:** حداقل `تفصیلی + معین + دوره مالی + سایر ابعاد معتبر`؛ مانده هر ترکیب مستقل (Σبدهکار − Σبستانکار) و مانده کل تفصیلی فقط تجمیع صحیح آن‌هاست بدون از بین رفتن جزئیات معین. موجودیت‌های حداقلی مدل: کدینگ کل/معین، تفصیلی و طرف‌حساب، ارتباط تفصیلی↔معین، سند و ردیف سند، گردش بدهکار/بستانکار، مانده تفکیکی، نگاشت حساب ERP↔CRM، دوره مالی و وضعیت سند، ابعاد تکمیلی. ابتدا ساختار موجود شناسایی شود و فقط کمبود واقعی با Migration افزایشی تکمیل شود؛ جدول/Provider/موتور موازی ممنوع.
- **معیار پذیرش:** ثبت و بازیابی پس از Refresh؛ ویرایش/حذف از مسیر DataProvider؛ نبود وابستگی داده اصلی به State؛ مانده مستقل هر (تفصیلی، معین)؛ حفظ جداول و روابط موجود؛ اجرای Migrationهای جدید؛ جابه‌جایی محلی↔سرور با تنظیمات؛ نبود داده ساختگی. فقط آزمون واقعاً اجراشده PASS است.

## E. گزارش و تحلیل
- توسعه گزارش منتظر اتصال واقعی DB نمی‌ماند: UI، قرارداد داده، فرمول Registry، داده DEMO، تست و ویوهای موردنیاز تکمیل شود.
- فرمول فقط در `src/lib/metricRegistry.ts` مرجع است؛ سند KPI با `npm run kpi:doc` تولید شود.
- Drill-down، فیلتر، مقایسه، روند و تشخیص ناهنجاری باید با ماهیت گزارش سازگار باشد.
- توان پرداخت در گزارش مالی به نقدینگی و تعهدات خود شرکت و پیش‌بینی نقد آزاد اشاره دارد؛ با اعتبار/سقف اعتبار مشتری یکی نیست.
- نبود Cost/Source/coverage باید در خروجی قابل مشاهده باشد.

## F. تجربه کاربری و دسترسی
- موبایل‌اول، RTL، Neo-Slate/Electric Indigo به‌عنوان هویت هدف، Light/Dark و دسترس‌پذیری.
- از پالت hardcoded در کامپوننت‌ها استفاده نکن؛ توکن معنایی.
- همه کنترل‌ها label/accessibility name، focus و اندازه لمس مناسب داشته باشند.
- ظاهر شیک نباید باعث حذف قابلیت یا پنهان‌شدن داده مهم شود.

## G. امنیت و حسابرسی
- مجوز ناشناخته و scope نامعتبر باید deny شود.
- UI guard جایگزین API authorization یا SQL RLS نیست.
- تغییر مالکیت، تأیید، حذف و عملیات حساس باید audit trail داشته باشد.
- اسرار و credential در سورس/مستندات/خروجی ZIP قرار نگیرد.

## H. تحلیل و قراردادهای داده
- هر Provider باید منبع، زمان دریافت، تازگی، پوشش و وضعیت خطا را آشکار کند.
- Cross-filter و Drill-down باید فقط با شناسه و رابطه معتبر داده کار کنند؛ فیلتر باید به همه نماهای وابسته درست منتقل شود.
- RBAC در سطح route، عملیات، داده و مقصد Drill-down enforce شود.

فقط پنج سند دستی وجود دارد (`INSTRUCTIONS.md`، `docs/MASTER_SPEC_FA.md`، `docs/CHECKLIST_FA.md`، `docs/CONSTITUTION_FA.md`، `docs/DESIGN_SYSTEM_FA.md`) به‌علاوهٔ سند تولیدی KPI. فایل مستند جدید نساز؛ وضعیت را فقط در Checklist ثبت کن؛ هر نوبت با ZIP معتبر پایان یابد.


## K. قانون اساسی پایش ERP و چرخه مغایرت
- منبع پایش فقط دیتابیس تجمیعی ERP معرفی‌شده توسط مالک است؛ اتصال ERP در CRM فقط‌خواندنی است. هیچ UPDATE/DELETE/INSERT مستقیم روی جداول منبع ERP مجاز نیست. اصلاح رسمی فقط در ERP و توسط کاربر مجاز انجام می‌شود؛ CRM پس از Sync مجدد نتیجه اصلاح را راستی‌آزمایی می‌کند.
- قبل از انتخاب CDC، Change Tracking، Timestamp یا Snapshot، قابلیت واقعی موتور/نسخه/مجوز/ساختار دیتابیس تجمیعی بررسی شود. روش انتخابی باید حذف، اصلاح، درج، تأخیر، قطع اتصال و replay را پوشش دهد. اگر حذف از منبع قابل تشخیص نیست، این محدودیت آشکار و BLOCKED/NOT VERIFIED ثبت شود؛ حذف را حدس نزن.
- هر چرخه Sync دارای شناسه، منبع، بازه/Checkpoint، زمان شروع/پایان، تعداد دریافتی/جدید/اصلاح‌شده/حذف‌شده/ردشده، checksum، خطاها و وضعیت نهایی باشد. اجرای مجدد یک Batch نباید اثر تکراری بسازد؛ داده قدیمی‌تر حق overwrite داده جدیدتر را ندارد.
- تغییرات داده باید فقط قوانین وابسته به همان موجودیت/حوزه را دوباره اجرا کنند؛ در صورت تغییر تعریف قانون، نسخه جدید قانون و دامنه بازاجرای آن ثبت شود. نتایج قبلی پاک نشوند. هر یافته دارای هویت پایدار و کلید منطقی یکتا (tenant + source + domain + rule + source entity identity + fingerprint/occurrence policy) باشد؛ کلید دقیق پس از شناخت Schema و سناریوها مستند شود.
- وضعیت «جدید» به معنی کشف جدید در چرخه جاری است، نه تعداد کل یافته‌های باز. شمارنده Badge باید از Query/Service پایدار و مجاز استخراج شود و تفکیک جدید، فعال، بحرانی و نیازمند اقدام را رعایت کند؛ شمارنده صفر فقط وقتی صفر واقعی است.
- یافته/مغایرت یک پرونده دارای lifecycle است. تغییر وضعیت، مشاهده، توضیح‌خواهی، ارجاع، تخصیص، تأیید، رد، استثنا، اصلاح، بسته‌شدن، بازگشایی و هر تلاش ناموفق باید actor/time/reason/evidence/version داشته باشد. تاریخچه حذف یا overwrite نمی‌شود.
- «تأیید با علت/استثنا» فقط برای همان یافته و با دامنه، مستند، تأییدکننده، تاریخ اعتبار و سیاست بازاعتبارسنجی مجاز است؛ تأیید نباید قانون را خاموش کند یا یافته‌های بعدی/تغییرات بعدی را بی‌اثر سازد. تأیید جایگزین اصلاح ERP نیست.
- حل‌شدن خودکار فقط پس از دریافت snapshot/رویداد معتبر جدید و اجرای مجدد همان قانون با نتیجه رفع‌شدن اثبات می‌شود. اگر داده منبع دیررس/ناقص/غیرقابل‌دسترسی است، پرونده «حل‌شده» نشود. یافته رفع‌شده از فهرست فعال خارج می‌شود ولی تاریخچه و occurrence حفظ می‌گردد؛ وقوع مجدد به پرونده/سابقه قبلی مرتبط و طبق سیاست بازگشایی می‌شود، نه اینکه سابقه پاک یا پرونده بی‌ارتباط تکراری ساخته شود.
- هر قانون باید شناسه پایدار، حوزه، نسخه، شرط/فرمول، پارامترها، شدت، دامنه شعبه/انبار/دوره، مسئول/مهلت، منبع و نگاشت داده، شواهد، پوشش و نتیجه آزمون داشته باشد. مقادیر تجاری مثل آستانه سود، سقف تخفیف، مهلت رسیدگی و دوره زمانی داخل کد ثابت ممنوع است.
- نبود جدول/ستون/ارتباط/داده لازم به معنی «ارزیابی‌نشده/منبع ناموجود» است، نه صفر خطا، سلامت یا PASS. برای هر قانون نگاشت دقیق schema با شاهد ثبت شود؛ هیچ نام جدول/ستون یا رابطه ERP حدس زده نشود.

## L. قانون اساسی علت‌یابی مالی و مدیریت پرسنل
- مانده بستانکار مشتری به‌تنهایی تخلف نیست. علت‌یابی فقط از اسناد واقعی، گردش بدهکار/بستانکار و ارتباط معتبر تفصیلی × معین × دوره انجام شود. دریافت تخصیص‌نیافته، پیش‌پرداخت، دریافت تکراری، برگشت فروش، سند اصلاحی، تفصیلی اشتباه، تخصیص به مشتری دیگر، اختلاف زمانی فروش/دریافت، انتقال مانده، چک و تسویه باید جداگانه بررسی شوند. هر علت با سند، مبلغ، تاریخ، منطق و سطح اطمینان ارائه شود؛ نبود شواهد کافی = «علت قابل تشخیص نیست/نیازمند بررسی».
- مسئول مالی می‌تواند «تأیید بستانکاری با علت و مستند» یا «اعلام مغایرت و اصلاح در ERP» را انتخاب کند. تأیید مدیر مجاز، رد، توضیح، مستند و نتیجه باید audit شود. هیچ تحلیل احتمالی هوش مصنوعی علت قطعی تلقی نشود.
- Person/Employee/UserAccount و نقش‌های عملیاتی باید تا حد ممکن بر هویت انسانی یگانه متصل باشند؛ کد ERP و داده محلی با source/origin مجزا نگهداری شوند. داده ERP read-only است؛ موجودیت CRM-owned فقط با منشأ `LOCAL` و قواعد یکتایی مشخص در جداول SQL Server خود CRM ذخیره می‌شود؛ منظور از LOCAL مالکیت دامنه است، نه ذخیره‌سازی مرورگر/دستگاه. تعریف هویت/پرسنل از تنظیمات سیاستی جداست؛ RBAC و سیاست دسترسی در تنظیمات باقی می‌ماند.
- آموزش، آزمون، تأیید مدیر و پلکان حقوق باید گردش نسخه‌دار و قابل حسابرسی داشته باشند. نمره/شرکت در آزمون به‌تنهایی مجوز ارتقا نیست؛ حدنصاب، تأیید مدیر، سیاست مصوب حقوق، تاریخ اثر و تأیید مجاز لازم است. هیچ پرداخت/تغییر حقوقی خودکار و بدون کنترل مجاز انجام نشود.
- اطلاعات حقوق، پرونده پرسنلی، آزمون و ارزیابی دارای مجوزهای جداگانه‌اند؛ UI guard به‌تنهایی کافی نیست و API/RLS باید آزمون شود.


## M. اجرای اتمی، عدم تکرار ممیزی و تکمیل عمودی
- ممیزی پایه فقط یک‌بار برای هر نسخه/ZIP انجام و نتیجه با نسخه، تاریخ، ابزار و دامنه در Checklist ثبت می‌شود. در نوبت‌های بعد، ممیزی فقط روی فایل‌ها، مصرف‌کنندگان، جدول‌ها و تست‌های متأثر از ردیف جاری انجام می‌شود؛ تکرار ممیزی کل سورس یا بازخوانی اسناد ممنوع است، مگر تغییر نسخه/درخواست صریح مالک/شاهد رگرسیون گسترده.
- هیچ فایل ناقص، نیمه‌جایگزین، truncate یا با حذف بخش‌های نامرتبط تحویل نمی‌شود. پیش از ویرایش، کل فایل در صورت نیاز معماری و محدودهٔ دقیق آن بررسی؛ تغییر با patch حداقلی انجام؛ سپس diff و ساختار فایل کنترل می‌شود. هر فایل باید از نظر import/export، نوع‌ها، خطاها، حالت خالی/بارگذاری/خطا، مجوزها، RTL و تست مرتبط کامل باشد.
- «تکمیل یک فایل» به‌تنهایی معیار تحویل قابلیت نیست: تمام فایل‌های وابستهٔ همان Vertical Slice (UI، سرویس/موتور، DataProvider/API، SQL migration، تست و مستندات) باید تا انتهای سناریوی قابل‌استفاده تکمیل شوند؛ سپس به قابلیت بعدی برو. تغییرات مستقل و پراکنده و رهاکردن نیمه‌تمام یک قابلیت ممنوع است.
- دادهٔ عملیاتی فقط از جداول SQL Server از مسیر DataProvider/Repository مجاز و با مجوز سمت سرور/RLS خوانده شود. نام جدول/ستون حدس زده نشود؛ Schema، کلید، رابطه، tenant، ایندکس و lineage پیش از استفاده بررسی شود. کمبود واقعی با Migration افزایشی، idempotent و قابل rollback تکمیل شود. عدم دسترسی به DB یا نبود جدول، به معنی BLOCKED/UNAVAILABLE است، نه مجوز خواندن Seed/IndexedDB.
- دادهٔ DEMO فقط در محیط تست/دمو با برچسب واضح و جداسازی tenant/source؛ هیچ مقدار نمونه‌ای در مسیر عملیاتی یا KPI واقعی وارد نشود. `null`/unknown جای صفر ساختگی است.
- قانون UI: پوسته، هدر شناور، منوی شیشه‌ای، توکن‌ها، رنگ، فونت و ساختار ناوبری قفل‌شده دست‌نخورده؛ فقط تغییرات صریحاً مصوب مالک مجاز. Landing هر فضای کاری آیکون‌محور، دسته‌بندی‌شده، RBAC-aware و کم‌تراکم است. کلیک کاشی فقط به Route/صفحهٔ همان قابلیت می‌رود.
- قانون «+» سراسری: تنها نقطهٔ ایجاد عملیات در هدر است و فهرست/فرم عملیات آن بر اساس Route فعلی، مجوز RBAC و وضعیت قابلیت به‌صورت پویا تعیین می‌شود (مشتریان→مشتری، اتوماسیون→تسک/گردش، جلسات→جلسه، کمپین‌ها→کمپین و ...). دکمهٔ ایجاد تکراری در بدنه صفحه ممنوع؛ کنترل‌های تخصصی داخل فرم/فرآیند که بخشی از خود عملیات‌اند استثنا هستند. اگر عملیات در صفحه‌ای مجاز نیست، گزینه نمایش داده نشود.
- قانون پروفایل: پروندهٔ مشتری و پروفایل کاربر/پرسنل باید از الگوی Entity 360 مصوب Design System الهام بگیرند: هویت/وضعیت، اطلاعات پایه، شاخص‌های واقعی، تایم‌لاین مستند، نمودارهای کوچک و اقدام مجاز؛ نه دادهٔ نمایشی و نه کارت‌های تزئینی.
- نمودار: ECharts و `echartsTheme.ts` موجود اولویت دارند؛ کتابخانهٔ نمودار موازی نصب/ساخته نشود. نمودار فقط از دادهٔ واقعی Provider، با واحد/بازه/Tooltip/Empty/Error/Loading و responsive RTL استفاده کند.
- مهارت طراحی: عامل باید وجود skill رسمی `ui-ux-pro-max` یا معادل مورد تأیید مالک را در محیط توسعه بررسی و در صورت وجود installer معتبر نصب و فعال‌بودنش را اثبات کند؛ نصب پکیج یا اجرای دستور ناشناخته/شبکه‌ای بدون اجازه ممنوع. نبود مهارت نباید به ادعای نصب منجر شود؛ از Design System پروژه پیروی و وضعیت را گزارش کند.
- محدودیت توکن/زمان: هیچ `npm install`، `npm ci`، build، typecheck یا کل تست‌ها بدون درخواست صریح مالک یا ضرورت مستقیم و ثبت دلیل اجرا نشود. ابتدا تست اختصاصی کم‌هزینه؛ تست‌های مرتبط حداکثر ۲–۳ مورد. ممیزی و خواندن تکراری ممنوع.
